# AGENTS.md

Working brief for an AI coding agent, not documentation for people (the README covers that): the rules, invariants and gotchas needed to change this project correctly without rediscovering them.

## Hard rules
- Commit, push, and publish only when the user says to ship; a mid-work commit is never the deliverable, because the user tests interactively first.
- Commit messages are short single-line conventional ones (`feat:`, `fix:`, `chore:`, ...), never with a `Co-Authored-By` trailer and never with a verbose body.
- Release flow, in this exact order: ask whether this shipment gets tests and write them only if the user says yes -> bump `version` in `Cargo.toml` -> `cargo fmt --check` clean, `cargo clippy-all` clean and `cargo test` green, which is also what refreshes `Cargo.lock` with the new version -> `cargo +1.88 msrv` clean, the only thing that proves the `rust-version` floor in `Cargo.toml` is real -> one commit -> `git push origin main` -> `cargo publish` (dry-run first, publishing is irreversible) -> tag only after publish succeeds with `git tag vX.Y.Z && git push origin --tags`; a tag must never point at a version that failed to publish, and the bump comes first because `cargo publish` fails on a `Cargo.lock` that still holds the old version.
- Tests are proposed at ship time and never before: the first step of the release flow is to ask the user, in plain words, whether this shipment gets tests, and they are written only on a yes, so the decision is always theirs but the question is never forgotten.
- Never write a test for behaviour that has not shipped yet, because code that is not in the last release tag is still being designed, and a test pinning a shape that is about to change is how a suite starts lying.
- A test may only assert something the README or `--help` promises, or a pure-logic invariant (parsing, generation, path resolution, validation); never the shape of a private function and never the specific diff that was just made, since those rot on the next refactor and teach nothing about whether the program works.
- Removing a promise from the README removes its tests in the same commit.
- A test may only write inside a temp directory it deletes, never a real config, data, cache or content directory and never a fixed path, so a machine is left exactly as it was before the suite ran.
- Never drive the interface to test it: build it, say what changed and what to look at, and let the user run it, because they see the screen instantly while an agent driving a pty or a tmux pane is slow and wrong about what it looks like; logic that is not visual can still be checked directly from `tests/`.
- Never `cargo install` to test: run the release binary at `./target/release/essh` directly, because installing replaces the binary on PATH with a work-in-progress build; install only when the user asks.
- `main` is protected: no force-push and no history rewrite, so a mistake is fixed with a forward commit.
- **How an error reads.** Lowercase, names things in backticks, says what to do next. When a program we ran is the thing that failed, the message carries that program's own words rather than a paraphrase: its stderr, blanks dropped, consecutive repeats collapsed (a tool called once per file says the same thing about each one), capped to a line count so it cannot fill the screen. A raw OS error reaching the user is a bug, not a message, and an errno is not a diagnosis.
- **Where an error appears: in a TUI.** One the user has to read is raised as an **alert** box (see the kinds of box below), never a status line: a status line is wiped by the next redraw, and a screen that comes back unchanged reads as a keypress that did nothing. The view holds it as an `Option<_>` that is handed keys before the view's own and drawn last, owning every key until dismissed while Ctrl-C still quits out from under it. Anything that hands the terminal over returns an outcome enum rather than a string, so the caller is made to decide rather than defaulting to silence: `Quiet` (it ran, nothing to say), `Note(String)` (a failure with nothing to explain, such as a tool quit with a non-zero code on purpose, which stays a status line), `Failed(_)` (has to be read). The box is raised only after the terminal is ours again, because a suspended child writes its complaint to the normal screen and we take that screen away in the same instant. `sluuz` is the reference: `tui::widgets::Modal`, `tui::difftool::DiffTool`.
- **The six kinds of box, and what a colour means.** Every overlay is one of six, and the kind fixes the border colour: a **gate** (red, two buttons, starts on **No**) in front of something destructive or irreversible; an **alert** (yellow, no buttons, dismiss only, scrolls) for a failure that already happened and has to be read; an **offer** (cyan, two buttons, starts on **Yes**) where the app volunteers a fix after something failed; a **picker** (cyan) to choose from a list the app already knows; a **form** (cyan) for typed fields and wizards; a **reader** (cyan) for a scrolling read-only body such as help. Red means you are about to lose something, yellow means something already went wrong and reading it costs nothing, cyan means the app is asking or offering with nothing at stake. What a box *does* is carried by its buttons and its default focus and never by colour alone, which is what tells a gate from an offer: red starting on No against cyan starting on Yes. A seventh kind is a house decision, not a local one: it goes into every crate's `AGENTS.md` or it does not get added.
- **What every box looks like.** One anatomy across every kind and every crate, so that only the colour and the buttons carry meaning: `Clear` first, centered, `Borders::ALL`; the title is `" name "`, spaced and lowercase, on the top border, and **nothing else is ever written on the border**, because a frame with a sentence along the bottom of it stops reading as a frame and starts competing with its own title; `Padding::new(2, 2, 1, 0)`, one blank row above the content and none below it, since the key line is already the last thing in the box and a blank under it only makes the frame look loose; the body left-aligned and wrapped with `Wrap { trim: false }`, wrapping off only for pre-formatted content that scrolls; the keys are the last row of the *body*, after a blank row, in `DarkGray` dimmed, which is a step below an unfocused field label (the default foreground, dimmed) on purpose - separation here is the blank row and the fixed position, never brightness, and anything brighter or tinted makes a guideline read as something worth reading; buttons are `" Yes (y) "` and `" No (n) "` so the label teaches the key, the picked one `bg(<the border colour>) + fg(Black) + BOLD` and the other `DIM`. The box is measured from its content: width clamped to 24..88, height the *wrapped* row count plus 3 for the two borders and the top padding row, capped at the whole screen and never at a fraction of it - a box is drawn over a `Clear` and owns the screen while it is up, so a fraction only decides in advance that a long one gets cut off. Counting unwrapped lines, or forgetting the chrome, is what clips the last row and leaves a modal looking unanswerable; a fixed height is the same bug waiting for a longer message. Ctrl-C escapes any box, and a key that means nothing to it is swallowed rather than dismissing it.
- **How a box looks is checked by looking at it, never by a test.** A `TestBackend` buffer holds only symbols, so it can never see a colour, a weight or a spacing, which is most of what is worth checking about an overlay. The verification surface is the rendered frame: run the tape whose shot covers the box and look at the PNG or GIF in `readme-assets/`, which an agent can open and read as well as a person can, so this is a real check rather than a hand-wave at somebody else. A test that asserts on a box's body text pins the wording instead of the behaviour, so every rewording breaks it while teaching nothing about whether the box works. Geometry is the one thing such a test could honestly assert - the bottom border on screen and the row above it not blank - and even that goes in only if the user asks for it at ship time.
- **A required field is marked with a red `*`, and nothing else is.** A wizard field carries the star only where the submit path really refuses a blank, so everything unmarked is provably optional and a label never also says "optional" - saying it twice is what makes the unmarked fields ambiguous. The star sits between the label and its colon and keeps its red while the label around it dims, because whether a field can be left blank is a property of the field and not of where the cursor is; the key row gains a plain-dim `* required` legend only when a visible field is starred, and is never tinted. The star and the check that enforces it are added in the same commit, or the form starts lying about what it needs.
- **How a form is laid out.** A wizard is two columns: labels on the left, values in one straight column that starts at 14 and is pushed out no further than 22 by a wide form, past which the labels are the ones that give way, since a single long label must never shove every value off the box. The label is a short noun and its colon, nothing else: what the field wants goes in the value column as a dim placeholder - what a blank submits, then the example - and it is gone the moment there is a value. Nothing in a row appears or disappears with the cursor, because a key printed on whichever row is focused makes every row grow and shrink as you move through the form, to say what the key line at the bottom already says. Guidance that is still true once a field is filled in is one dim note line under the fields, never a parenthetical in four labels that are pre-filled anyway. The block reserves the rows of the tallest shape the form can rebuild into, so answering one field never resizes the frame under the cursor. A two-option toggle is drawn as the house buttons, the picked one filled; a one-of-many pick is its value between dim guillemets, so the two never read as each other.
- **Where an error appears: in a CLI.** It goes to stderr and the process exits non-zero. Stdout is the command's output and nothing else, because `slu ls | grep x` and every script like it must never find a complaint mixed into the data, and a failure that still exits 0 is a lie a script has no way to catch. Say it in one line of our own words, then the failing program's own words under it when there are any; a panic and its backtrace are never the user-facing path, so anything we can predict is caught and worded before it gets there.
- No em-dashes anywhere (code, comments, README, `--help`, crate description, commit messages, prose), because they read as AI-generated text; use `-` instead.
- Fix the root cause, and if a workaround must ship say the word "workaround" out loud so a silent patch never passes as a real fix; the same goes for lints, where an `#[allow]` is never the answer and the code it points at gets fixed or deleted.
- `TODO-LIST.md` (gitignored) holds one-line ideas, and the line is deleted when the idea ships.
- `demo/` holds the screenshot and GIF rig: `stage.sh` builds a fake `~/.ssh` in `demo/home` (fake hosts, generated keys, seeded history, placeholder tunnels) with HOME and every XDG variable redirected into it, and the VHS tapes render `readme-assets/` from it. A tunnel, a mount and a login cannot be faked, so `raspi` points at a real machine only when `ESSH_DEMO_HOST` is set; nothing personal is ever in the repo. `stage.sh down` unmounts anything under the stage before deleting it and refuses if that fails, because a recursive delete walks straight through a mountpoint and onto the remote side - that is not hypothetical, it cost a real machine its dotfiles.
- The demo rig is standardised across every crate in this directory, and the three parts that make the frames match must stay identical: the staged shell wears the invented `user@host` prompt written by `write_demorc`, every tape sets `Set Theme "Catppuccin Mocha"` (VHS's own default is a near-black that is harsher to read than Catppuccin's `#1e1e2e`), and every tape sets `Set FontFamily "JetBrainsMono NF"`. It is not about hiding a username, which is no leak - the pictures are a build output, and one that comes out different on every machine that regenerates it is not reproducible.
- Everything staged runs under `env -i` with a complete allowlist, never the real environment plus overrides, because an exported variable nobody thought of is exactly how a real config dir, a real endpoint or a real key ends up in a frame. The rig also writes only inside the stage, so nothing of the renderer's is touched on disk.
- Teardown goes through `assert_safe_to_delete`, word-for-word the same function in every crate's rig: the stage path must be absolute, must not be a system directory or the renderer's home, must resolve through its symlinks to a tree carrying the marker file the build stamped, and must have nothing mounted under it, with `rm -rf --one-file-system` behind that. Test the refusals after touching them, never just the happy path - an sshfs mount inside a staged home, torn down with a plain `rm -rf`, has already deleted the dotfiles on the machine at the far end.
- `.nocommit/` (gitignored) holds reference material used only to inform work here - other projects, notes, drafts - and never ships; keep it out of anything user-facing (commit messages, code, comments, README, `--help`), since a reference to material nobody outside this machine can see means nothing to them and just clutters the record.
- Tests never touch the real `~/.ssh`: use `App::empty()` and the `sshcfg` `*_in(path, ...)` helpers, which keep everything on temp files and in-memory data.
- Do not grow the CLI. It holds connect, `ls`, `cp` and `update` only, all things faster to type than to click. Anything a user would have to look up belongs in the TUI, which is the whole point of the tool.

## Invariants and gotchas
- When adding a host with an IdentityFile: if exactly one shared block (a `Host a b c` line with 2+ concrete aliases) already sets that same key, append the new alias to that block and give the new host a block without its own IdentityFile; otherwise write a self-contained block. Never join a one-alias block (that is a normal per-host block, not a group) and never touch a block when zero or several match, so the tool only ever extends a group the user already made shared.
- When a host sets a `RemoteCommand`: write `RequestTTY yes` beside it (`render_block_lines` does), or the forced command comes back without a terminal and the shell has no prompt and no line editing. ssh refuses a command line on top of one (`Cannot execute command-line and remote command.`), so `essh <alias> <cmd>` fails on such a host by design; `ssh -N` is unaffected, so tunnels still work, `scp` passes `-oRemoteCommand=none` itself, and our sshfs argv passes it too because sshfs does not. Never append `RemoteCommand` to a shared `Host a b c` block: unlike an IdentityFile it is per-host, and it would force the command on every alias in the group.
- When adding a host from a paste: a `[user@]host[:port]` typed into the add wizard's Alias field is split across the fields when you leave it (`sshcfg::parse_target`), but only in the add wizard - doing it while editing would rename an existing host behind the user's back - and only for a string that really is a destination, since a plain word is somebody typing an alias.
- When listing hosts: one alias may be defined across several `Host` blocks (a per-host block for HostName/User plus a shared `Host a b c` block adding a common IdentityFile); `merge_hosts` collapses them into a single entry with ssh's first-value-wins per field, so never emit one entry per block.
- When editing or deleting a host: it only works when the alias is the sole name on its `Host` line, and a shared `Host a b` block is refused because one alias cannot be rewritten in isolation. Every config write backs up first to `config.bak.<epoch>` and rewrites only the touched block, never reformatting the file.
- When touching tunnels: they assume key or agent auth, since a detached `ssh -N` cannot answer a password prompt. After spawning, the code waits about a second and checks `/proc/<pid>`, so a dead-on-arrival tunnel returns ssh's stderr instead of leaving a phantom entry.
- When touching tunnel or mount liveness and kill: it reads `/proc` and shells out to `kill` and `fusermount`, so it is Linux-only and macOS or BSD need a different check first.
- When generating an RSA key: pass `-b 4096`, because `ssh-keygen -t rsa` defaults to 3072 and RSA is only chosen for legacy hosts that will be kept for years. ed25519 has one fixed size, so it takes no `-b`.
- When labelling anything user-facing: write `meaning (real command)`, such as `mount a remote folder locally (sshfs)` or `fix "host key changed" (ssh-keygen -R)`. Command-only is unreadable to a beginner, and verb-only teaches nothing and leaves them stuck without the tool.
- When an action needs a value the app already knows, such as a config host or a key, open a picker instead of a text field, because retyping a known alias is slower and typo-prone. The add/edit-host IdentityFile and ProxyJump fields are typed OR picked: `Ctrl-o` on them opens a picker of `~/.ssh` keys, or of the config's own aliases (both via `PickerAction::FillField`), while a typed value still works for anything custom.
- When mounting: refuse with an install hint if `sshfs` is not on PATH, default the mountpoint to `<mount_root>/<host>` (`~/sshfs/<host>` out of the box - absolute, because a relative default put mounts wherever essh happened to be launched from) so leftovers stay grouped, and expand a typed `~` with `sshcfg::expand_tilde` (children are spawned without a shell, so `~/dir` would otherwise become a directory literally named `~`), and `remove_dir` the mountpoint after a successful unmount. `remove_dir` only removes an empty directory, so a mount placed over a dir with real content is never deleted.
- When adding a TUI action: `c` creates in every view (`n` is deliberately unbound), `y` copies to the clipboard (the public key text on Keys) while `Y` is the loud version that writes on another machine (ssh-copy-id, with the picker showing the login each alias resolves to, since `admin@box` and `pi@box` are different authorized_keys files), `d` deletes, kills or unmounts, `r` refreshes and `e` edits. Hosts has no `y`: it copied `ssh <alias>` to the clipboard, which Enter already does better from inside the tool. Lowercase is always the local, harmless copy and uppercase the one that touches a remote, so the pair is never guessed backwards. Destructive persistent actions such as deleting a host get a yes/no confirm gate, while trivially redone ones such as kill and unmount act at once.
- When filtering: `/` starts a query over the current list only, and it is dropped when you switch view, because a filter you cannot see the origin of silently hides rows. A selection indexes the *filtered* rows, so every `selected_*` goes through `*_rows()`; indexing the raw vec picks the wrong entry the moment a filter hides anything. `filter::matches` filters and never re-ranks, since the Hosts order is already earned by `history`.
- When touching host order: the Hosts list is sorted by `history::rank` (most recently connected first, then never-used alphabetically), so `refresh_hosts` must call `sort_hosts` and `App::new` must load the history *before* the first refresh. `essh ls` stays alphabetical: a script's output must not depend on what you did yesterday.
- When adding a setting: put it in `settings.rs` only - a field, a default, a `set` arm and a `rows()` entry - and the Settings tab, the file and the `d`-to-default key all pick it up with no UI work. A cycled setting takes `choices` and changes in place on Enter; a typed one opens a one-field wizard. Every change saves immediately, so there is no unsaved state and no save key. A setting the running app acts on must also be re-applied in `apply_settings`, or it only takes effect at the next launch.
- When defaulting a wizard field from a setting: put the value in the field's `default` and read it back from there (`fields[i].default`) rather than reaching for `Settings` again downstream, so the live preview and the command that runs cannot disagree. The mountpoint and the sftp-server path both work this way.
- When an action makes something (a tunnel, a mount), jump to its view with `goto_view` and select the new row: `select_tunnel` right away, and `new_mount` + `settle_new_mount` for a mount, which only exists in `/proc/mounts` after the suspended `sshfs` returns. Assigning `self.view` directly skips the filter clearing and can land you on a tab that hides the very thing you just made.
- When touching the detail panel: it renders for Hosts, Keys and Mounts (a tunnel already says everything it knows on its one line) and only above `MIN_WIDTH_FOR_DETAIL`, so a narrow terminal keeps a readable list. It reads only what is already loaded - never a fresh command, and never any I/O on a mountpoint, since a stale sshfs mount blocks `stat` and `df` forever and would hang the draw loop.
- When showing a path: `sshcfg::collapse_tilde` is display only (the inverse of `expand_tilde`), so `Mount::describe` and the panel agree with each other and with what the user typed, while `Mount::local` stays absolute because that is what `fusermount` is handed.
- When touching reachability: probes run on background threads and report over an mpsc channel, tagged with `reach_gen`; an answer from an older generation is dropped rather than repainting a list that has moved on. The event loop polls while `probing()` is true and blocks otherwise, so the idle cost stays zero. A TCP connect answers "is anything listening", never "can I log in", and the labels must not claim more.
- When yanking: the clipboard is whichever of `wl-copy`, `xclip`, `xsel`, `pbcopy` is on PATH, and the status names it (`copied … (wl-copy)`); with none installed we say which ones would work rather than failing silently. Nothing is bundled and nothing is installed.
- TUI navigation: `j/k` and the arrows move, `h/l`, the arrows and Tab switch view, and the Ctrl-chords navigate too. Inside a wizard `h/j/k/l` are typed text, so fields move with `Ctrl-j/k`, `Ctrl-arrows` or Tab. A `Kind::Choice` field is the exception: it holds no text, so `h/l` and the arrows (with or without Ctrl) cycle its answer and you leave it with Tab, Enter or the vertical keys.
- The add/edit-host wizard stars the Alias alone, because `submit_prompt` refuses only that one: a `Host raspi` with no HostName is valid whenever the alias itself resolves, so starring HostName would mean enforcing it and taking that host away from the TUI, and a blank User is not an omission either - it is ssh using your login name, which is the whole point of leaving it out.
- Wizard fields are `Kind::Text` or `Kind::Choice` (cycled in place), and `shown_when` hides one until another field's choice selects it. Hidden fields keep their slot so field indices stay stable; `visible`, `step` and `on_last_field` are what keep navigation and Enter from landing on them.
- Every overlay goes through the house box in `tui::widgets` (`box_block`, `box_buttons`, `box_hint`, `box_width`, `box_inner_width`, `box_height`, `box_area`), never a hand-rolled `Block`. Measure the body with `wrapped_line_count(text, box_inner_width(width))` and hand the *wrapped* count to `box_height`, which adds the chrome: a sudo mount's preview is wider than the box, and counting lines clipped the key line off. `wrapped_line_count` counts real columns (leading spaces included), so do not switch it back to `split_whitespace`. The percentage-width `centered` and `PROMPT_PCT` were deleted rather than kept beside it, because two ways to size a box is how the padding stopped being accounted for in one of them.
- When mounting as root: sshfs's channel has no tty, so `sudo` cannot prompt, and the wizard offers exactly one sudo mode - `-o sftp_server=sudo <path>`, which needs a NOPASSWD sudoers line scoped to the sftp server. Do not add a "send the password" mode: every way of feeding one from here (piping it to `sudo -S`, priming the ppid ticket) puts the password in a command line, where `ps` shows it to every user on both machines. Hiding it would take owning the SSH client, not a flag.
- Status messages are transient: set them with `set_status` and they clear after `STATUS_TTL`, so a stale result never reads as the current state. The event loop polls while a message is showing and blocks otherwise, so an idle TUI costs nothing.
- Failures the user must act on never sit in a status that flashes past. One we can classify into a next step becomes an **offer** (`Confirm::offer`, cyan, starts on Yes): a busy unmount offers `fusermount -u -z`, and a connect that exits 255 is probed with `changed_host_key` and, if the key changed, offers `ssh-keygen -R`. One with nothing to propose becomes an **alert** (`tui::alert`, yellow, dismiss only), which is where a program that could not be started at all ends up. The probe runs only after a failed connect, so the success path costs nothing.
- Wizards show a live `command_preview` rebuilt from the current fields, so the user sees the exact `ssh-keygen`/`sshfs`/`ssh -L` command as they type. Keep the preview's value resolution identical to `submit_prompt`, or the preview lies.
- `Confirm` is two things told apart by its `danger` flag: `Confirm::new` is a gate, red, starting on **No**, so a reflex Enter never fires something destructive; `Confirm::offer` is the app proposing a fix after a failure, cyan, starting on **Yes**, because accepting it costs nothing and you asked for it by pressing Enter in the first place. Both answer to `y`/`n` directly, move with `h/l`, the arrows and Tab, cancel on Esc, and ignore any other key so a stray press cannot answer the question.
- The help overlay is measured from its own content like every other box, so adding a line needs no height edit - but the pane fits a 30-row terminal *exactly*, with nothing spare. Adding a line means merging or dropping another one, or the last row goes off the bottom of a standard terminal, and nothing will tell you: count the lines before adding one.
- Interactive children (connect, keygen, copy-id, mount) run suspended: leave the alt-screen, run them so they can prompt for passwords, then restore. Tunnels are detached and skip this.
- When suspending the TUI: call `show_cursor()` after leaving the alt-screen, because the draw loop hides the cursor and leaving the alt-screen does not restore it, so the child would otherwise run with an invisible cursor.
- When testing the TUI: driving it through `script` or a pty is unreliable because the alt-screen is not captured, so assert rendering with ratatui's `TestBackend` instead.

## Build / lint / test
- `cargo build --release`, binary at `target/release/essh`.
- `cargo clippy-all` is the lint pass, aliased in `.cargo/config.toml` to `clippy --release --all-targets -- -D warnings`; use it rather than a bare `cargo clippy`, which skips `tests/` and `examples/` and only warns where the release flow wants a failure.
- `cargo test`.
- `cargo fmt` formats the crate and `cargo fmt --check` fails when anything has drifted; the whole crate is rustfmt clean, so formatting is never a judgement call and never a review comment.
- `cargo +1.88 msrv` checks the crate against the `rust-version` floor it advertises (alias in `.cargo/config.toml`), and when the code starts needing a newer compiler both that floor and the toolchain in this line move together.
- Tests cover the `sshcfg` parser and its block surgery on temp files, plus `TestBackend` render and keymap tests in `tui/tests.rs`; when something genuinely cannot be tested (terminal lifecycle state, for example), say so rather than skipping it silently.

## Overview
Layout:
- `src/main.rs` - the clap `Cmd` enum and the dispatch match, nothing else.
- `src/commands/<verb>.rs` - one file per CLI command (`connect`, `ls`, `cp`, `selfcmd`), each exposing `run`.
- `src/tui/` - the toolbox: `mod.rs` owns `App`, the event loop and the terminal handling, `input.rs` dispatches keys per view, `wizard.rs` is what a submitted prompt does, `prompt.rs` the field machinery, `picker.rs` and `confirm.rs` their overlays, `mount_spec.rs` the sshfs command a mount wizard builds, `render.rs` the frame, `detail.rs` the panel beside the list, `filter.rs` what `/` keeps, `widgets.rs` the domain-blind furniture, `connect.rs` reading ssh's failure output, `tests.rs` the `TestBackend` tests.
- Domain modules at the top level: `sshcfg` (parsing and editing `~/.ssh/config`), `keys`, `tunnels`, `mounts`, `history` (when you last connected where), `reach` (background ssh-port probes), `clip` (the system clipboard), `settings` (`~/.config/easyssh/settings`).


`easyssh` is a Rust CLI and TUI that makes ssh simple: one binary `essh` in place of `ssh`, `ssh-keygen`, `ssh-copy-id`, `scp` and `sshfs`, plus hand-editing `~/.ssh/config`. It is a smart frontend rather than a reimplementation, so every action shells out to the real tools and ssh-agent, keys and existing config keep working. Bare `essh` opens a ratatui toolbox with Hosts, Keys, Tunnels and Mounts tabs and their wizards, while the CLI keeps connect, `ls`, `cp` and `update`. Crate `easyssh`, binary `essh`, repo `git@gitlab.com:safteinzz/easyssh.git`, published on crates.io under AGPL-3.0-only.
