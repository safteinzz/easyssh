# AGENTS.md

Working brief for an AI coding agent, not documentation for people (the README covers that): the invariants, gotchas and decisions needed to change *this project* correctly without rediscovering them.

## Hard rules

- `demo/` holds the screenshot and GIF rig: `stage.sh` builds a fake `~/.ssh` in `demo/home` (fake hosts, generated keys, seeded history, placeholder tunnels) with HOME and every XDG variable redirected into it, and the VHS tapes render `readme-assets/` from it. A tunnel, a mount and a login cannot be faked, so `raspi` is a throwaway sshd in a podman container on 127.0.0.6 (invented user, hostname and home), and a staged `ssh` wrapper points every ssh at the staged config and known_hosts, for the reason in the next line. `stage.sh down` unmounts anything under the stage before deleting it and refuses if that fails, because a recursive delete walks straight through a mountpoint and onto the remote side - that is not hypothetical, it cost a real machine its dotfiles. `up`, `shell` and `run` also refuse while any sshfs mount outside the stage is up, because essh lists every mount in `/proc/mounts` and a tape's Enter once unmounted a real one.
- **A staged `HOME` does not move ssh's own config.** Not a quirk of one build: OpenSSH expands a leading `~` through `tilde_expand` in `misc.c`, which takes the home directory from `getpwnam()`/`getpwuid()` (`pw->pw_dir`) and never reads `$HOME`, and `ssh.c` builds the user config path with `tilde_expand_filename(_PATH_SSH_USER_CONFFILE, ...)`. Verified here too: `HOME=/tmp/nowhere ssh -G -v somehost` reads `/home/<you>/.ssh/config` (OpenSSH_10.4p1). What it means for the rig: essh reads the staged config, because it honours `HOME`, while the `ssh` it spawns reads the renderer's real one, so a `RemoteCommand` or a `ProxyJump` in your own `~/.ssh/config` can break a staged mount or tunnel while the frame shows a host that has neither. That cost a render of `mounts.png` once. `ssh -F <file>` does override it, but production essh must not pass `-F`, so the rig's answer is to keep the renderer's own config out of the way rather than to work around it in the tool.
- Tests never touch the real `~/.ssh`: `App::empty()` and the `sshcfg` `*_in(path, ...)` helpers keep everything on temp files, and the visual surface is checked by rendering a tape and looking at the frame, never by driving a pty.
- Do not grow the CLI. It holds connect, `ls`, `cp`, `completions` and `self` (`self update`, `self check`) only, all things faster to type than to click, plus `completions`, which sets up Tab completion once. Anything a user would have to look up belongs in the TUI, which is the whole point of the tool.

## Invariants and gotchas
- When adding a host with an IdentityFile: if exactly one shared block (a `Host a b c` line with 2+ concrete aliases) already sets that same key, append the new alias to that block and give the new host a block without its own IdentityFile; otherwise write a self-contained block. Never join a one-alias block (that is a normal per-host block, not a group) and never touch a block when zero or several match, so the tool only ever extends a group the user already made shared.
- When a host sets a `RemoteCommand`: write `RequestTTY yes` beside it (`render_block_lines` does), or the forced command comes back without a terminal and the shell has no prompt and no line editing. ssh refuses a command line on top of one (`Cannot execute command-line and remote command.`), so `essh <alias> <cmd>` fails on such a host by design; `ssh -N` is unaffected, so tunnels still work, `scp` passes `-oRemoteCommand=none` itself, and our sshfs argv gets the same immunity through `-o ssh_command=ssh -o RemoteCommand=none`, which is the only route that works: libfuse checks sshfs's options strictly and answers an ssh option with `fuse: unknown option(s)` instead of forwarding it, so passing `-o RemoteCommand=none` to sshfs directly fails every mount. That wrapper is added **only for a host that really forces a command** (`sshcfg::forces_command`, asked once when the wizard opens and carried in `Action::Mount`): on every other mount it is a no-op that doubles the length of the command the preview exists to teach. It cannot be answered from the host list alone, because `merge_hosts` drops the pattern blocks and a `Host *` can force one; a pattern too rich for `glob_match` answers yes, since a needless `RemoteCommand=none` costs a longer line and a missing one costs a mount that fails with nothing readable. Never append `RemoteCommand` to a shared `Host a b c` block: unlike an IdentityFile it is per-host, and it would force the command on every alias in the group.
- When adding a host from a paste: a `[user@]host[:port]` typed into the add wizard's Alias field is split across the fields when you leave it (`sshcfg::parse_target`), but only in the add wizard - doing it while editing would rename an existing host behind the user's back - and only for a string that really is a destination, since a plain word is somebody typing an alias.
- When listing hosts: one alias may be defined across several `Host` blocks (a per-host block for HostName/User plus a shared `Host a b c` block adding a common IdentityFile); `merge_hosts` collapses them into a single entry with ssh's first-value-wins per field, so never emit one entry per block. First-wins holds inside a block too (`set_once`), and a `Match` line ends the Host block above it, since what follows applies only when its condition holds.
- When editing or deleting a host: it only works when the alias is the sole name on its `Host` line, and a shared `Host a b` block is refused because one alias cannot be rewritten in isolation. Every config write backs up first to `config.bak.<epoch>` and rewrites only the touched block, never reformatting the file. Inside the block an edit works line by line (`set_key`): a form key is rewritten on its own line and only when its value changed, a new one goes after the block's last setting, and a blank field removes its key, where only the first `IdentityFile` goes because ssh tries every one and the form shows only the first. Comments, keys the form has no field for and a `RequestTTY` the user set stay exactly where they were; a blank Port writes no Port line at all.
- When touching tunnels: every forward you open is kept, as a line in `~/.config/easyssh/tunnels` (`-L 8080:localhost:80 raspi`, plus ` = a label` where one was typed), while `~/.local/state/easyssh/tunnels.tsv` holds what is running right now. What identifies a forward is what it does - flag, spec, host - so that triple is the line's key and `entries()` joins the two files on it; a name is an optional label over the top and never an identity, which is why renaming cannot collide and why nothing has to be named to be listed. `Entry::label()` spells an unnamed row out from its ports (`raspi:80 → 8080`, `3000 → raspi:9000`), so the list reads without the file being annotated. Anything found running with no line of its own is adopted into the file by `entries()`, so "running" and "kept" can never disagree and a row can always be turned back on. Enter is on/off, and `D` deletes the line behind a red gate, stopping it first if it is up; `d` is unbound there because a key that stops on the first press and deletes on the second is one press from losing the line. The line is written before the tunnel is started, because a forward that will not come up is exactly the one you want left in the list to fix. They assume key or agent auth, since a detached `ssh -N` cannot answer a password prompt. After spawning, the code waits about a second and checks the pid, so a dead-on-arrival tunnel returns ssh's stderr instead of leaving a phantom entry.
- When touching tunnel or mount liveness and kill: it reads `/proc` and shells out to `kill` and `fusermount`, so it is Linux-only and macOS or BSD need a different check first. A tunnel counts as alive only while `/proc/<pid>/cmdline` still holds *this* forward's flag, spec and host, never merely because `/proc/<pid>` exists: a pid in the state file can outlive a reboot, and a recycled one would otherwise read as up and be what Enter or `D` kills.
- When generating an RSA key: pass `-b 4096`, because `ssh-keygen -t rsa` defaults to 3072 and RSA is only chosen for legacy hosts that will be kept for years. ed25519 has one fixed size, so it takes no `-b`.
- When labelling anything user-facing: write `meaning (real command)`, such as `mount a remote folder locally (sshfs)` or `fix "host key changed" (ssh-keygen -R)`. Command-only is unreadable to a beginner, and verb-only teaches nothing and leaves them stuck without the tool.
- When an action needs a value the app already knows, such as a config host or a key, open a picker instead of a text field, because retyping a known alias is slower and typo-prone. The add/edit-host IdentityFile and ProxyJump fields, and the tunnel wizard's Host field, are typed OR picked: `Ctrl-o` on them opens a picker of `~/.ssh` keys, or of the config's own aliases (both via `PickerAction::FillField`), while a typed value still works for anything custom.
- When mounting: refuse with an install hint if `sshfs` is not on PATH, default the mountpoint to `<mount_root>/<host>` (`~/sshfs/<host>` out of the box - absolute, because a relative default put mounts wherever essh happened to be launched from) so leftovers stay grouped, and expand a typed `~` with `sshcfg::expand_tilde` (children are spawned without a shell, so `~/dir` would otherwise become a directory literally named `~`), and `remove_dir` the mountpoint after a successful unmount. `remove_dir` only removes an empty directory, so a mount placed over a dir with real content is never deleted. Every mount is kept like a tunnel: a `local <- host:path` line in `~/.config/easyssh/mounts` (plus ` (sudo <server>)`), keyed by the local folder as `/proc/mounts` spells it (`fs::canonicalize` after the folder is made, since a trailing slash or a symlinked root would otherwise never match), written before the mount is tried, with Enter mounting or unmounting and `D` deleting like Tunnels, and live mounts with no line are adopted by `mounts::entries()`. The sudo server lives only in that line, because `/proc/mounts` does not show it. sftp has no `~`, so a typed leading `~/` is dropped from the remote path (`mount_spec::remote_path`) and `Mount::describe` puts it back for display.
- When adding a TUI action: `c` creates in every view (`n` is deliberately unbound; on Tunnels it opens the wizard with the host as a field, since that tab has no host to read), `y` copies to the clipboard (the public key text on Keys) while `Y` is the loud version that writes on another machine (ssh-copy-id, with the picker showing the login each alias resolves to, since `admin@box` and `pi@box` are different authorized_keys files), `d` deletes, kills or unmounts (on Tunnels and Mounts it is `D` instead, and Enter is the on/off switch), `r` refreshes and `e` edits. Hosts has no `y`: it copied `ssh <alias>` to the clipboard, which Enter already does better from inside the tool. Lowercase is always the local, harmless copy and uppercase the loud one: it touches a remote, or, for `D`, loses a line you keep, so the pair is never guessed backwards. Destructive persistent actions such as deleting a host get a yes/no confirm gate, while trivially redone ones such as kill and unmount act at once.
- When filtering: `/` starts a query over the current list only, and it is dropped when you switch view, because a filter you cannot see the origin of silently hides rows. A selection indexes the *filtered* rows, so every `selected_*` goes through `*_rows()`; indexing the raw vec picks the wrong entry the moment a filter hides anything. `filter::matches` filters and never re-ranks, since the Hosts order is already earned by `history`.
- When touching host order: the Hosts list is `Host::jumped()` first, then `history::rank` (most recently connected first, then never-used alphabetically) or the alias, per the `host_order` setting, so `refresh_hosts` must call `sort_hosts` and `App::new` must load the history *before* the first refresh. A host with a `ProxyJump` is a route rather than a machine you sit on, so the whole group sits under the direct ones - the sort is the whole grouping, with no column and no header, because a taxonomy column that repeats on every row costs the alias and target columns more width than the distinction is worth. `essh ls` stays alphabetical and ungrouped: a script's output must not depend on what you did yesterday.
- When adding a setting: put it in `settings.rs` only - a field, a default, a `set` arm and a `rows()` entry - and the Settings tab, the file and the `d`-to-default key all pick it up with no UI work. A cycled setting takes `choices` and changes in place on Enter; a typed one opens a one-field wizard. Every change saves immediately, so there is no unsaved state and no save key. A setting the running app acts on must also be re-applied in `apply_settings`, or it only takes effect at the next launch.
- When defaulting a wizard field from a setting: put the value in the field's `default` and read it back from there (`fields[i].default`) rather than reaching for `Settings` again downstream, so the live preview and the command that runs cannot disagree. The mountpoint and the sftp-server path both work this way.
- When an action makes something (a tunnel, a mount), jump to its view with `goto_view` and select the new row: `select_tunnel` right away, and `new_mount` + `settle_new_mount` for a mount, which only exists in `/proc/mounts` after the suspended `sshfs` returns. Assigning `self.view` directly skips the filter clearing and can land you on a tab that hides the very thing you just made.
- When touching the detail panel: it renders for Hosts, Keys and Mounts (a tunnel already says everything it knows on its one line) and only above `MIN_WIDTH_FOR_DETAIL`, so a narrow terminal keeps a readable list. It reads only what is already loaded - never a fresh command, and never any I/O on a mountpoint, since a stale sshfs mount blocks `stat` and `df` forever and would hang the draw loop.
- When showing a path: `sshcfg::collapse_tilde` is display only (the inverse of `expand_tilde`), so `Mount::describe` and the panel agree with each other and with what the user typed, while `Mount::local` stays absolute because that is what `fusermount` is handed.
- When touching reachability: probes run on background threads and report over an mpsc channel, tagged with `reach_gen`; an answer from an older generation is dropped rather than repainting a list that has moved on. The event loop polls while `probing()` is true and blocks otherwise, so the idle cost stays zero. Names are resolved by a `getent ahosts` child killed at the probe timeout, never by `getaddrinfo` in-process: glibc's `exit` waits on every stdio lock, and `mdns4_minimal` holds one while avahi times out, which made quitting take five seconds with a `.local` host in the config. A TCP connect answers "is anything listening", never "can I log in", and the labels must not claim more. A host with a `ProxyJump` is never probed at its own address, which is resolved on the jump host and would answer about the wrong machine: `sshcfg::first_hop` gives the first hop of its chain instead, so the dot is the jump's answer and wears a filled `◆` rather than a `●` to say the question was asked one machine away, with every word of the panel's line naming the jump. A route the config cannot resolve (a jump that is itself jumped, an alias that is not defined) is `Reach::Indirect`, a dim `·` distinct from the hollow `○` of a probe in flight, and claims nothing. Probes are started by `App::new`, by `r`, and on return from anything that took the terminal away, since a dot learned before a connect is a claim about a world we stopped watching.
- When touching image paste (`paste.rs`, `P` on Hosts): it exists because Claude Code on Linux reads a pasted image only by running `xclip -selection clipboard -t TARGETS -o` (piped into `grep image/…`) and then `xclip -selection clipboard -t image/png -o` (found with `strings` on its binary; the `image/bmp` and `wl-paste` fallbacks it chains after them are left to the real tools). A host is enabled by a line in `~/.config/easyssh/paste` (`alias /abs/remote/dir`), written only after the installer reports success, and matched against the destination exactly as typed, since an alias logs in as the one user the stand-in was installed for. Enabling sits behind a red gate because it lets that host (root included) read your clipboard image while you are connected; disabling drops the line first, which alone stops the forwarding, then removes the stand-in. The stand-in (`paste/xclip.sh`, marked by the `essh image-paste stand-in` line) goes to `~/.local/bin/xclip`, never over an `xclip` that lacks the marker, and passes every other call to the next `xclip` in PATH; it treats only grep's "no match" as "not ours" and refuses to pass a call it was itself handed (`ESSH_XCLIP_PASSED`), because a failing grep once made it `exec` itself forever. The install and remove scripts travel base64-encoded in the ssh command line (`echo … | base64 -d | sh`), so stdin stays the terminal for a password and no fish or csh login shell parses them, with `RemoteCommand=none`, `RequestTTY=no` and `ClearAllForwardings=yes`; their stdout is captured (`PendingRun::paste`) and read as `essh-paste:` lines. The remote socket directory is absolute and learned from the installer: ssh rejects a relative `-R` socket path and would expand `~` on this side, and a path past `sun_path` (`MAX_SOCKET_PATH`) makes ssh abort the whole login (`Bad remote forwarding specification`), not just the forward. sshd decides whether a stale socket is replaced (its own `StreamLocalBindUnlink`, default no; the client's option only covers `-L`) and never deletes one when a login ends, so every login binds a fresh `<epoch>-<pid>.sock` and the stand-in tries the newest first, deleting the ones that refuse a connection; a forward that fails is a warning ssh prints, never a failed login, so never add `ExitOnForwardFailure`. For an enabled host `essh <host>` does not `exec`: it spawns ssh, serves the clipboard from a thread on a 0600 socket under `$XDG_RUNTIME_DIR/easyssh`, catches SIGINT and SIGQUIT with `signal-hook` and does nothing with them, never `SIG_IGN`, which ssh would inherit and then stop honouring Ctrl-C, and exits with ssh's code or `128 + signal`. The TUI's Enter shares `paste::serve_for` and drops the `Forward` the moment the login returns. Every other host keeps the plain `exec`.
- When yanking: the clipboard is whichever of `wl-copy`, `xclip`, `xsel`, `pbcopy` is on PATH, and the status names it (`copied … (wl-copy)`); with none installed we say which ones would work rather than failing silently. Nothing is bundled and nothing is installed.
- TUI navigation: `j/k` and the arrows move, `h/l`, the arrows and Tab switch view, and the Ctrl-chords navigate too. Inside a wizard `h/j/k/l` are typed text, so fields move with `Ctrl-j/k`, `Ctrl-arrows`, `↑↓` or Tab. Typed text is edited through `tui::line_edit` and nowhere else, in every form field and in the `/` filter: a cursor (`back`, characters after it, so code that assigns a value without knowing about it leaves the cursor at the end) and readline's emacs keys: `←→`, `Ctrl-b/f`, `Alt-b/f`, `Home`/`End`, `Ctrl-a/e`, Backspace, `Ctrl-h`, Delete, `Ctrl-d`, `Ctrl-w` (back to a space), `Alt-Backspace` and `Alt-d` (a word), `Ctrl-u`. Not `Ctrl-k`: it stays the previous field, the up half of `Ctrl-j/k`. The form's key line names only Enter, Esc and the `*` legend, since editing and moving keys are known or looked up, not taught. A `Kind::Choice` field is the exception: it holds no text, so `h/l` and the arrows (with or without Ctrl) move its answer and you leave it with Tab, Enter or the vertical keys. A two-option choice is drawn as the house buttons, so there the arrows stop at the edge instead of wrapping; a longer one cycles between guillemets.
- The host form's ForwardAgent is a no/yes toggle that opens on what ssh would really use (`sshcfg::forward_agent_for`, wildcard blocks included) and writes a line only when the answer differs from that, so an untouched toggle adds nothing and a `ForwardAgent no` the user wrote is never stripped by an edit. A change an earlier block would override is refused before anything is written (`check_forward_agent`), because a save that ssh ignores reports a change that never happens; this is the agent reaching a machine the user shut it out of. The add form never writes `no`, since a new host has no line of its own to cancel. A socket path already in the config becomes a third option.
- The add/edit-host wizard stars the Alias alone, because `submit_prompt` refuses only that one: a `Host raspi` with no HostName is valid whenever the alias itself resolves, so starring HostName would mean enforcing it and taking that host away from the TUI, and a blank User is not an omission either - it is ssh using your login name, which is the whole point of leaving it out. A public key in IdentityFile is refused (`keys::is_public_key`) with the private path to use instead, and a path that does not exist is saved with a yellow warning, except one ssh expands itself (`%d`, `${HOME}`, quotes), which cannot be checked from here.
- Wizard fields are `Kind::Text` or `Kind::Choice` (cycled in place), and `shown_when` hides one until another field's choice selects it. Hidden fields keep their slot so field indices stay stable; `visible`, `step` and `on_last_field` are what keep navigation and Enter from landing on them.
- Every overlay goes through the house box in `tui::widgets` (`box_block`, `box_buttons`, `box_hint`, `box_width`, `box_inner_width`, `box_height`, `box_area`), never a hand-rolled `Block`. Measure the body with `wrapped_line_count(text, box_inner_width(width))` and hand the *wrapped* count to `box_height`, which adds the chrome: a sudo mount's preview is wider than the box, and counting lines clipped the key line off. `wrapped_line_count` counts real columns (leading spaces included) and starts a row at every `\n`, so do not switch it back to `split_whitespace`: an alert body is several lines, and measuring it as one clipped its last rows. The percentage-width `centered` and `PROMPT_PCT` were deleted rather than kept beside it, because two ways to size a box is how the padding stopped being accounted for in one of them.
- When mounting as root: sshfs's channel has no tty, so `sudo` cannot prompt, and the wizard offers exactly one sudo mode - `-o sftp_server=sudo <path>`, which needs a NOPASSWD sudoers line scoped to the sftp server. Do not add a "send the password" mode: every way of feeding one from here (piping it to `sudo -S`, priming the ppid ticket) puts the password in a command line, where `ps` shows it to every user on both machines. Hiding it would take owning the SSH client, not a flag.
- Status messages are transient: set them with `set_status` and they clear after `STATUS_TTL`, so a stale result never reads as the current state. The event loop polls while a message is showing and blocks otherwise, so an idle TUI costs nothing.
- Failures the user must act on never sit in a status that flashes past. One we can classify into a next step becomes an **offer** (`Confirm::offer`, cyan, starts on Yes): a busy unmount offers `fusermount -u -z`, and a connect that exits 255 is probed again with `connect::diagnose` (BatchMode, plus `-o RemoteCommand=none` because ssh refuses a command line on a host that forces one before it even connects), which offers `ssh-keygen -R` for a changed key and `IdentitiesOnly yes` for an agent that offered too many keys, and explains refused, unresolved, unreachable and keys-only failures in an alert with ssh's own lines. One with nothing to propose becomes an **alert** (`tui::alert`, yellow, dismiss only), which is where a program that could not be started at all ends up. The probe runs only after a failed connect, so the success path costs nothing.
- Wizards show a live `command_preview` rebuilt from the current fields, so the user sees the exact `ssh-keygen`/`sshfs`/`ssh -L` command as they type. Keep the preview's value resolution identical to `submit_prompt`, or the preview lies.
- `Confirm` is two things told apart by its `danger` flag: `Confirm::new` is a gate, red, starting on **No**, so a reflex Enter never fires something destructive; `Confirm::offer` is the app proposing a fix after a failure, cyan, starting on **Yes**, because accepting it costs nothing and you asked for it by pressing Enter in the first place. Both answer to `y`/`n` directly, move with `h/l`, the arrows and Tab, cancel on Esc, and ignore any other key so a stray press cannot answer the question.
- The help overlay is measured from its own content like every other box, so adding a line needs no height edit - but the pane fits a 30-row terminal *exactly*, with nothing spare. Adding a line means merging or dropping another one, or the last row goes off the bottom of a standard terminal, and nothing will tell you: count the lines before adding one.
- Interactive children (connect, keygen, copy-id, mount, the image-paste install and removal) run suspended: leave the alt-screen, run them so they can prompt for passwords, then restore. Tunnels are detached and skip this. A run whose output is read afterwards (`PendingRun::paste`) captures stdout and stderr and prints its label first, since ssh still prompts on the tty.
- When suspending the TUI: call `show_cursor()` after leaving the alt-screen, because the draw loop hides the cursor and leaving the alt-screen does not restore it, so the child would otherwise run with an invisible cursor.
- When testing the TUI: driving it through `script` or a pty is unreliable because the alt-screen is not captured, so assert rendering with ratatui's `TestBackend` instead.

## Build / lint / test
- `cargo build --release`, binary at `target/release/essh`.

## Overview
Layout:
- `src/main.rs` - the clap `Cmd` enum and the dispatch match, nothing else.
- `src/commands/<verb>.rs` - one file per CLI command (`connect`, `ls`, `cp`, `completions`, `selfcmd`), each exposing `run`.
- `src/tui/` - the toolbox: `mod.rs` owns `App`, the event loop and the terminal handling, `input.rs` dispatches keys per view, `wizard.rs` is what a submitted prompt does, `prompt.rs` the field machinery, `picker.rs` and `confirm.rs` their overlays, `mount_spec.rs` the sshfs command a mount wizard builds, `render.rs` the frame, `detail.rs` the panel beside the list, `filter.rs` what `/` keeps, `widgets.rs` the domain-blind furniture, `line_edit.rs` one line of typed text with a cursor and the emacs keys, `connect.rs` reading ssh's failure output, `paste_run.rs` what `P` does and how its remote script's report is read, `tests.rs` the `TestBackend` tests.
- Domain modules at the top level: `sshcfg` (parsing and editing `~/.ssh/config`), `keys`, `tunnels` (the forwards you keep and the ones that are running), `mounts`, `history` (when you last connected where), `reach` (background ssh-port probes), `clip` (the system clipboard), `paste` (image paste into a remote Claude Code: the enabled-hosts file, the clipboard server a login carries, and the remote scripts in `src/paste/`), `completion` (Tab completion through clap_complete's `COMPLETE=<shell> essh`, whose script `essh completions <shell>` prints and `--add` writes a loader line for once, with a bash adapter that glues `host:path` back together after bash splits it at the colon), `settings` (`~/.config/easyssh/settings`).


`easyssh` is a Rust CLI and TUI that makes ssh simple: one binary `essh` in place of `ssh`, `ssh-keygen`, `ssh-copy-id`, `scp` and `sshfs`, plus hand-editing `~/.ssh/config`. It is a smart frontend rather than a reimplementation, so every action shells out to the real tools and ssh-agent, keys and existing config keep working. Bare `essh` opens a ratatui toolbox with Hosts, Keys, Tunnels and Mounts tabs and their wizards, while the CLI keeps connect, `ls`, `cp`, `completions` and `self` (`self update`, `self check`). Crate `easyssh`, binary `essh`, repo `git@gitlab.com:safteinzz/easyssh.git`, published on crates.io under AGPL-3.0-only.
